## Shared integration architecture

1. **Dependency readiness:** define a versioned catalog of required capabilities, configuration checks, entitlement evidence, ownership, cost/quota decisions and staging acceptance. Readiness states: not configured, configured but unverified, staging accepted, enabled, degraded, revoked. A present API key is not proof of licensing, reachability, sender verification, correct scopes or operational readiness. Safe diagnostics return booleans/codes/timestamps, never secret values.
2. **Connections:** bind provider account, scopes, capability set and connection generation to the workspace and authorized account. Use a server-only secret reference/encrypted credential design with explicit key custody and rotation. Do not put refresh tokens, API keys or signing secrets in browser settings, VITE variables, exports, normal audit text or committed fixtures. Choose the credential store during implementation; do not assume a particular vault is provisioned.
3. **Durable work:** reserve a bounded attempt transactionally, persist its source/version and operation ID, release the transaction before network I/O, then record a provider outcome using the exact lease/generation. Declare attempt/time/response limits, expiry, cancellation and permitted replay. Current actor/workspace access, destination, consent/purpose, holds and source must pass again immediately before the call. This is a final gate at dispatch; the database cannot atomically prevent a revocation that races an already-started external request.
4. **Remote outcomes:** distinguish queued, leased, deferred, provider accepted, delivered, bounced, suppressed, failed and ambiguous. Provider acceptance is not delivery. A timeout after possible acceptance must become ambiguous; reconcile through provider IDs/idempotency where supported or require reviewed recovery. Do not silently resend or claim exactly-once transport. The existing transaction-only test transport remains separate.
5. **Callbacks and sync:** verify the provider's specified signature/token, timestamp/replay rules and workspace/connection binding before processing. Deduplicate event IDs and handle reordered callbacks. If the provider lacks trustworthy callback verification, select an authenticated reconciliation path instead of treating an arbitrary callback as authoritative. Return quickly after durable intake, fetch authoritative changes, renew subscriptions and reconcile missed events in bounded steps.
6. **Lifecycle/privacy:** use current identity roots and retained aliases for reads, but invalidate pending work after merge/source/permission/connection changes. Do not automatically retarget a send to a survivor. Add every new candidate-linked attempt, event, message, attachment, credential-related receipt and sync item to relevant D7 and operations inventories; decide D6 disclosure scope and external deletion responsibilities explicitly. Recapture existing scopes when these sources change. Full recovery includes private schemas, receipts, cursors, lease/sequence state, encrypted credential material/key references and private object versions.
7. **Experience:** show configuration, sandbox/test and live states distinctly. Keep manual scheduling, reviewed text import and existing internal tasks usable during outages. Present one actionable next step with safe diagnostics. An enabled switch cannot stand in for acceptance; expired/disconnected integrations must not claim live availability or verified outcomes.

These are new implementation contracts, not a declaration that a connector framework already exists. Prefer thin domain interfaces for delivery, mailbox, calendar, processing and signing; avoid one generic adapter that obscures their different side effects and recovery rules.

## Stage 1: concrete first implementation slice

The first slice should be a **provider-neutral integration control and delivery sandbox**, leaving existing production flags paused. It can be implemented without buying a service or entering an API key.

- Add a bounded administrator readiness surface linked from Settings → Integrations: owner, purpose/capabilities, missing configuration, last redacted diagnostic, connection generation and acceptance evidence. Use current server roles/MFA and never echo credentials.
- Define delivery interface operations for prepare/dispatch/reconcile/callback normalization with a capability declaration (idempotency support, callback authentication and delivery evidence). Use fake network fixtures that can accept then time out, fail transiently, return duplicates, reorder events and revoke a connection. Do not ship an unrestricted endpoint accepting arbitrary recipients/URLs.
- Generate an additive Supabase migration when this slice starts. Proposed private storage: workspace connection metadata/secret references, leased live-intent snapshots, attempts, incoming-event receipts and reconciliation state. Final tables/API names, bounded pages and privacy additions must be recorded in its checklist; these proposed structures are not created by this plan.
- Reuse candidate UUID, reviewed contact references, purpose preferences, outbound holds, version checks and actor operation receipts. Separate sandbox/test evidence from live-intent history and preserve existing Stage 3 test semantics.
- Add a bounded server dispatcher with an allowlisted adapter and network timeouts; the local fictional adapter records an outcome without contacting recipients. Provider selection comes later. Keep final network authorization and lease completion tests distinct from database preparation tests.
- Deliver the UI, contracts, negative tests, migration/privacy inventories and rollout/rollback checklist together. Failed acknowledgement preserves an exact retry; ambiguous dispatch exposes reconciliation, not an ordinary Send again button.

Exit: an administrator can inspect readiness, a recruiter can prepare an authorized fictional delivery intent, and the bounded sandbox runner demonstrates acceptance/ambiguity/reconciliation without a real send. Mark the resulting code milestone sandbox-complete; mark live transport pending until provider acceptance passes. Do not call this groundwork document implementation completion.

## Current provider facts checked

The architecture intentionally accounts for the following current documented behavior; no provider is recommended or selected:

- Google Calendar notification channels expire and must be replaced; notifications identify change but require a follow-up resource fetch. Plan connection-bound intake, renewal and reconciliation. [Google Calendar push documentation](https://developers.google.com/workspace/calendar/api/guides/push)
- Microsoft Graph change-notification subscriptions have limited lifetimes and require renewal. Model subscription expiry separately from account OAuth expiry. [Microsoft Graph change notifications](https://learn.microsoft.com/en-us/graph/change-notifications-overview)
- VirusTotal's public API excludes commercial products/services and certain business workflows. Preserve the existing business-entitlement gate and hash-only optional reputation behavior; private ClamAV remains the release gate. [VirusTotal Public vs Premium API](https://docs.virustotal.com/reference/public-vs-premium-api)
- Supabase documents project SAML SSO with provider configuration and usage pricing. Verify the target project's entitlement and IdP integration before implementation/activation; ordinary OAuth sign-in is not a substitute for organizational SAML SSO. [Supabase SAML SSO](https://supabase.com/docs/guides/auth/enterprise-sso/auth-sso-saml)

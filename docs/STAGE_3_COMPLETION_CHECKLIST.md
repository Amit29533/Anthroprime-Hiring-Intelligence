# Stage 3: communication test workflows

Baseline: local Stage 2 `4881cf1`, 7 October 2026. This implements continuation milestone 3 from the [five-phase audit](FIVE_PHASE_IMPLEMENTATION_AUDIT_2026_10_07.md#next-build-order), corresponding to the communication slice of original Phase 5. It does not activate a delivery provider. Local commits only; no push or deployment.

## Implemented behavior

| Area | Contract |
| --- | --- |
| Templates | Administrator-owned plain-text versions with stable keys, purpose, message kind, enabled state, subject/body and four professional/context placeholders. Unknown placeholders, markup, header newlines and oversized text are rejected. Edits append a version with actor/time and invalidate old queued previews. |
| Kinds | Custom, application acknowledgement, interview invite/reminder, freshness check and redeployment. Applications require a recorded candidate/demand consideration; interview messages require a scoped future Scheduled interview. These are manual reviewed intents, not automatic acknowledgements or calendar invitations. |
| Preview | Server rendering from candidate name/Anthro-ID, scoped demand title and interview time. A dated confirmed active email is required; primary email alone is not considered confirmed. The recipient, rendered content, purpose and template version are visible before queue confirmation. |
| Consent | Explicit current recruiting-contact or marketing consent for the template purpose. Future grants do not qualify; revocation/expiry wins on equal dates. Candidate opt-out, outbound hold, Unavailable status, retired identity and obsolete/disabled template suppress eligibility. No inferred consent from applications. |
| Preferences | Append-only sourced purpose/email opt-out and UTC contact-window observations with actor/time. A merged identity's latest preference remains applicable until a later explicit observation replaces it. Re-enabling a preference does not grant consent. Candidate self-service belongs to Stage 4. |
| Intents | Explicit recipient-by-recipient confirmation of the reviewed source fingerprint, frozen content/recipient, scheduling within 30 days and seven-day expiry after scheduled availability. Pending duplicates and equivalent recent test records are rejected. Failed acknowledgement retries reuse the exact request and timestamp. |
| Segments | Server-side name/Anthro-ID, exact status and tag filtering before 25-row recipient pages. Selecting a recipient does not queue anything; each recipient still requires a preview and explicit confirmation. No bulk or automatic campaign execution. |
| Worker | Five-minute Netlify scheduled function, existing service credentials, at most 20 intents per call (database maximum 50), workspace → candidate → intent locks and skip-locked traversal. Policy defaults paused. Paused workspaces are excluded from selection so they cannot block active test queues. |
| Execution gates | Recheck issuing editor membership, contact, consent, preference, hold, identity, template, scoped context, source fingerprint and expiry. Changed or ineligible sources are suppressed rather than silently re-rendered. Missing context is isolated to its intent. Quiet windows and daily candidate frequency limits defer without a transport attempt. |
| Test outcomes | Deterministic success, first-attempt transient failure, or permanent failure selected by administrator test policy. Success is **Test recorded**, never Delivered. Each attempted simulation has a unique durable attempt receipt, time and SHA-256 of its frozen JSONB preview. There is no network send, email provider response, bounce or open-tracking claim. |
| Recovery | Bounded automatic transient backoff, administrator-reviewed retry of an unexpired Failed intent, maximum six total attempts, and editor cancellation of pending/failed intents. Source changes require a new reviewed intent. Cancellation and recovery have reason, server audit and actor-bound durable operation receipts. |
| Policy | Administrator opt-in/pause, simulation outcome and daily candidate test limit (1–20; default 3). Optimistic policy fingerprints prevent a stale configuration from undoing another administrator's change. Existing opt-in privileged MFA applies to policy, template and manual retry actions. |
| History/health | Workspace outbox exposes bounded metadata; candidate history exposes frozen previews and attempt receipts. Latest worker run, statuses, reasons, due/expiry times and attempts are visible. History preserves retired-identity intent evidence without transferring queued work to the survivor. |
| Privacy | D7 inventory grows from 48 to 52 categories: communication preferences, intents, attempts and candidate-linked operation receipts. D6 explicitly excludes these records for separately reviewed disclosure. Workspace templates/policy/worker health are not automatically candidate-linked inventory categories. |

## Access and experience

The cloud paged repository overview hosts the communication workspace; Candidate 360 has a Communication tests tab. Administrators manage policy/templates and retries; recruiters preview/queue, record sourced preferences and cancel their workspace's pending/failed intents; viewers only read. Assessor, sales and external client accounts cannot invoke the full communication APIs. Raw private tables and rendering/worker helpers are denied to browser roles; only guarded public invoker APIs are exposed. Worker execution is granted to service_role only.

The seven tables have private-schema RLS and revoked raw browser access. Read and mutation boundaries use the existing authoritative full-role membership guard, candidate scope, server audit and transactional receipts. There is no provider credential or service key in the browser. Typed financial fields are not available as template variables. Arbitrary authored text is not automatically classified: authorized staff must not insert restricted compensation or other private content into shared templates/messages.

Failed forms preserve drafts and exact retry operations. Source/template conflicts require discarding the failed draft, refreshing and reviewing the current preview/version; policy and template changes are never silently adopted. A pending schedule is shown in local browser time for entry and stored as a timestamp; contact windows are explicitly UTC, without inferred candidate timezone or DST handling. Template placeholders are candidateName, anthroId, demandTitle and scheduledAt only. No arbitrary variable, arbitrary recipient, attachment, public link generation or HTML rendering is supported.

Pages contain at most 25 recipients/intents; the template catalog is capped at 100 keys. Context selectors show up to 100 demands and 100 recent candidate interviews per title search; narrowing the title search finds contexts beyond the initial subset. Rendered subject/body limits are 200/12,000 characters. At most 20 new candidate intents can be prepared in a rolling 24 hours. The daily execution limit counts test records in a rolling 24 hours, not attempts or real deliveries.

## Operational model and limits

The test transport runs entirely inside the PostgreSQL transaction. A transaction failure rolls back attempts and state together; retries can inspect the committed receipt. No external side effect exists between claiming and completion, so this stage needs neither a provider lease nor an ambiguous remote acknowledgement reconciliation protocol. This is not a claim of exactly-once email delivery. Real transport requires its own delivery adapter, leases, provider idempotency, bounce/suppression callbacks, unsubscribe links and reconciliation acceptance before activation.

Policies pause execution but retain queued history. Expired queues are suppressed when an enabled worker next examines them; pause does not extend expiry. A recorded test remains historical after later consent/source changes and is not live delivery. Automatic applications/interview triggers, freshness campaigns, surveys and candidate self-update proposals are not enabled by this stage. Existing internal reminder/freshness task workers keep their separate behavior.

The new worker uses the same Supabase server configuration and adds one Netlify function, bringing packaging to 18 functions. Netlify scheduled functions run automatically on published deploys; preview/branch invocation is manual. Verify its Scheduled badge and Run now behavior using the [official scheduled-function documentation](https://docs.netlify.com/build/functions/scheduled-functions/). No new provider/account/package is required. Database bounds do not prove production latency; measure representative histories and queues before activation.

# Feature Equivalence Verification — ECOD vs. Zoho Recruit & the ECOD Blueprint

Refreshed 28 September 2026 · Code reviewed: `codex/remaining-features-phase-1` based on `031ec39`; Phase 1 changes are uncommitted

> **Blueprint source:** `ECOD_Talent_Intelligence_Repository_Product_Blueprint.docx` (v1.0, 18 September 2026) lives on the repository's `main` branch (commit `910ece0`). The full text was extracted and reconciled section-by-section in matrix section N below.

**Method:** Zoho Recruit's feature inventory was taken from Zoho's own plan-comparison page (full module/feature matrix), Zoho's staffing-agency feature pages, Zoho help documentation (resume parser, calendar sync, sourcing bot) and independent 2026 reviews. Each Zoho/blueprint capability was checked against the current code in `src/`, `supabase/` and `tests/` — not against marketing claims. PGlite migration tests cover local database behavior; this audit did not exercise the provisioned Supabase Auth, Storage or PostgREST deployment.

**Status legend:**
✅ Equivalent exists · 🟡 Partial (some of the capability exists) · ❌ Missing · ⚙️ Different by design (deliberate non-AI/deterministic alternative)

## 1. Executive summary

The audit checks **97 Zoho Recruit capabilities** and all **123 requirements** of the ECOD Product Blueprint v1.0 against the current implementation. _Refreshed 28 September 2026 after implementation batches 1–21: the current blueprint matrix is 83% weighted-equivalent; the blueprint's §15 R1 scope checklist is green. Historical batch notes are retained at the end of this document._

| Verification                       | ✅ Equivalent | 🟡 Partial | ⚙️ By design | ❌ Missing | Weighted coverage |
| ---------------------------------- | ------------- | ---------- | ------------ | ---------- | ----------------- |
| **Zoho Recruit** feature set (A–M) | 25            | 46         | 2            | 24         | **52%**           |
| **ECOD Blueprint v1.0** (N.1–N.14) | 83            | 36         | 1            | 3          | **83%**           |

**ECOD today ≈ a strong "repository-first talent intelligence core":** reusable candidate records, CSV/CV ingestion, search and local TF-IDF retrieval, explainable matching, demand pipelines, assessments, interviews/offers, governance tools, public careers and candidate self-service portals, plus workspace-level tenant isolation. It covers many recruiter-side ATS basics, but is not a substitute for an integrated communications suite, client/vendor CRM portals or enterprise-scale governance.

**The largest gaps vs. Zoho Recruit, in order of recruiter impact:**

1. **Resume handling is now partial** — upload, reviewable parsing, storage and search-inside shipped (batch 2), paste-a-forwarded-email inbox groundwork shipped (batch 10); automatic IMAP/webhook inbox ingestion is still open.
2. **Interviews module is new and recruiter-side** — scheduling, panels, structured feedback, invite drafts and one-way .ics import/export shipped (batches 5 and 10); live two-way calendar sync, video interviews and automated notifications remain open.
3. **External-facing surfaces are started** — public careers site (batch 8), self-serve status (batch 10) and a signed-in candidate portal with availability self-service (batch 11) shipped; client login portals and vendor portals remain.
4. **No integrated communication layer** — mailto drafts and one-way `.ics` import/export exist, but there is no server-side email delivery/inbox sync, mass messaging, SMS/WhatsApp or telephony.
5. **Automation engine is grounded but client-side** — condition-based workflow rules with task/note/tag/field-update actions shipped (batch 10); server-side execution, alerts, assignment/approval rules and webhooks remain.
6. **Thin customization layer** — saved views, tags and custom fields for candidates/demands shipped; custom modules, broader module-level fields and a layout editor remain open.
7. **Staffing-agency CRM depth is partial** — consent-gated submission packs, recruiter-recorded client decisions/free-text feedback, generated offer letters, client account/contact records and first-class placement/commercial outcomes have shipped; client-facing review, a client login portal and e-sign execution remain.
8. **No Zia-style AI** — no model-generated summaries, scoring or writing; local deterministic TF-IDF/natural-language retrieval is not a hosted embedding or AI layer, and a sourcing chatbot remains absent.

**Remaining gaps vs. the ECOD Blueprint after implementation batch 13:**

1. **Hosted semantic index (§5, §11, Phase 1.5)** — in-browser TF-IDF vector ranking and similar-talent retrieval shipped; a hosted embedding index for cross-workspace semantic search remains.
2. **API surface (§14)** — `api_changes_since` and paginated `api_changes_page` RPCs ship the workspace feed; candidate/demand `externalId` fields exist. A general REST wrapper, external-mapping registry and integration reconciliation remain open.
3. **Governance depth (§12)** — user/role administration shipped in batch 17 (invite, role change, access removal, last-admin guard, full audit trail). Server-side malware scanning, encrypted/scheduled backups with restore verification, export DLP/rate limits and SSO/MFA enrolment remain open. CSV provenance stamps and manual backup/restore exist, but do not provide those operational controls.
4. **Key screens (§8, R2 scope)** — public careers and candidate self-service portals shipped (batches 8 and 11) and the Clients screen shipped (batch 16); client and vendor _login_ portals remain outstanding.
5. **History and measurement depth (§7, §17)** — structured histories and current analytics are in place; per-skill evidence versioning, automated archival/purge, time-to-submit and cohort conversion remain.

- **Batch 21 shipped (28 Sep 2026):** the skills intelligence model (blueprint §6, §7, and the §14 entities Skill / PersonSkill / SkillEvidence). Migration 025 adds three tables. `skillEvidence` has **UPDATE and DELETE revoked from `authenticated` outright**, exactly like `history`, so append-only is a property of the database rather than a UI convention — correcting the record means adding a better observation. `personSkills` is a **derived** view maintained by a trigger: proficiency comes from the strongest evidence with recency only as a tie-break (§5: "a recent validated assessment should outrank self-declared skill"), and confidence and validation are conclusions the database draws, never values a client asserts — there is a test that overwrites them by hand and proves the next observation corrects them. - **Batch 22 shipped (28 Sep 2026):** branded client-ready candidate profiles (Zoho E6) — the artefact a staffing agency actually sends. A bug found while writing it is now a named test: `consentForProfileSharing()` returns the latest consent _record_, which is truthy even when it is a revocation, so the gate had to be the evaluated state rather than the presence of a row. **Contact details and the current employer are withheld by default** (sending a client a candidate's mobile number is how an agency loses its fee), and anonymisation hides the name _and_ the current employer together, because role plus company identifies a person anyway. **Compensation is admin-only and still off by default**; current CTC is unpresentable under every combination of options. Unverified facts are printed as such rather than implied to be checked. The preview iframe is the document — a test asserts the download is byte-for-byte what was on screen — and every export is audited with the disclosure list. Deliberately not included: DOCX/PDF binary generation; print-to-PDF is the PDF path, and claiming a generated DOCX without the machinery to produce one would be a false promise. 26 new tests (15 domain, 11 user-flow); **381 tests total**.

- **Batch 23 shipped (28 Sep 2026):** Excel (`.xlsx`) import (blueprint N53 §8 "Import: CSV/XLSX and CV bulk upload", supporting §16 scenario N91). Recruiters work in Excel; "export as CSV first" pushed a conversion step — and its encoding and date-format failures — onto the user. `src/xlsx.js` reads a workbook directly with **no new dependency**, reusing the minimal ZIP reader already proven for DOCX (`documents.js`) and adding the two things a spreadsheet needs that a Word file does not: the shared-string table and date detection. Cells are placed by their `r="B7"` reference rather than by position, so a gap in a row cannot shift data into the wrong column; dates are resolved through `styles.xml` (built-in and custom formats) into ISO dates instead of arriving as serial numbers like `45901`; repeated headers are disambiguated rather than overwriting each other; formula cells read as their stored value and `#REF!` errors become blanks so the existing missing-field check catches them; row numbers in the error report are the spreadsheet rows a user can actually see. A workbook enters the **same** mapping, preview, duplicate-resolution and error-report pipeline as a CSV — proved by driving the real Import screen. Inflated parts are capped so a zip bomb cannot exhaust the tab. Stated limits rather than silent behaviour: first worksheet only (a multi-sheet workbook says which one it used and that the rest were ignored), no legacy binary `.xls`, and dates before 1900-03-01 land a day early because Excel's serial 60 is a 29 February 1900 that never existed. 23 new tests (17 unit against real byte-built ZIP archives, 6 user-flow); **404 tests total**.

- **Batch 24 shipped (28 Sep 2026):** employee and partner referrals (Zoho D6) — one of the most-used ATS modules, and in most organisations the highest-quality hiring source. Migration 026 adds a `referrals` table plus a **write-only** anonymous `api_public_refer` RPC so employees who are not ATS users can refer from the careers page. The design takes one problem seriously: **a referral is a third party's contact details, offered by somebody else.** The referred person has not consented and may not know. So a referral is stored in its own table and is _never_ a candidate record; promoting one is a deliberate recruiter action that writes a consent record with the stated basis in the same save; the anonymous RPC cannot read anything back, because a referral list is a list of people who never opted in; and a duplicate submission returns success **without** revealing that the person is already in the pipeline. Rewards are tracked as state only — amounts and payment are payroll's business, and implying we have paid somebody would be worse than tracking nothing. Rates are withheld below three resolved referrals in both the leaderboard and the headline stat, from a single shared constant, so one lucky hire is never shown as a 100% scheme. 25 new tests (8 PGlite, 9 domain, 8 user-flow); **434 tests total**.
- **Bug found and fixed during batch 24:** `loadData()` returned `makeSeed()` **unnormalized** on a fresh demo workspace, and `makeSeed()` only produces tables it has sample data for. Any newer table was therefore missing its key, and the first save to one threw `Cannot read properties of undefined`. This had broken **saving a custom report on a fresh demo workspace since batch 20**, and was missed because the report UI test used a stubbed save rather than the real one. A regression test now asserts every table in `TABLES` is an array after a fresh `loadData()`.

- **Phase A shipped (28 Sep 2026):** day-to-day friction removers, identified by walking a recruiter's working day rather than the feature matrix. No migration. (1) **Cross-entity global search** — the top-bar box previously reached candidates only, so finding a demand or client meant knowing which page to be on first. It now searches seven entity types with weighted ranking (exact > starts-with > word-boundary > substring), grouped results and keyboard navigation. Admin-only figures — `expected`, `current`, `budget`, `internalCost`, portal `statusToken` — are on a never-indexed list, because _matching_ on a value discloses it; a test asserts a recruiter typing a real budget number finds nothing. (2) **A working notification bell** — it previously just navigated to Activities. It now counts only what is actionable today, and shows no badge at all rather than a zero. Requisition approvals are shown only to admins, since only they can clear them. (3) **A personal work queue** on the dashboard. Ownership in this release is a _text_ field, not a user id, so "assigned to me" can only be a best-effort name match; rather than hide that, `ownerLooksUnmatched()` detects when a workspace has owners but none resemble the signed-in user, and the UI says so instead of showing an empty queue that would read as "no work". 31 new tests (20 domain, 11 user-flow); **465 tests total**.

- **Phase B shipped (28 Sep 2026):** bulk operations. Every list action was previously one record at a time apart from export and a status change. `src/bulk.js` is a pure **planner**: it returns the exact rows that would be written _and_ the rows that would be skipped with a reason, so nothing happens until the user has seen what will happen — a bulk action that silently no-ops on half a selection is worse than one that refuses, because the user believes it worked. Skip reasons are grouped ("12 already tagged") rather than listed row by row. Edits carry an undo payload captured from the rows as they were; shortlisting is deliberately **not** undoable, because undoing it would mean deleting pipeline rows from a table this product never deletes from. 21 new tests (12 domain, 9 user-flow); **486 tests total**. Three defects were found and fixed during the work, two of them mine: the undo affordance vanished the moment it was needed because applying clears the selection, which unmounted the bar (undo is now owned by the parent); an early `return null` sat above a `useMemo`, changing the hook count between renders; and — a testing lesson worth recording — `assert.equal(domNode, null)` exhausts memory when it fails, because Node tries to serialise a jsdom element's circular graph for the diff. All such assertions across the suite were rewritten as boolean comparisons.

- **Phase C shipped (28 Sep 2026):** scheduling. (1) A **week calendar** on the Interviews page. A list cannot show a clash — two interviews at 3pm on different rows look fine until somebody misses one — so the grid flags any overlap that shares a person, counting the _candidate_ as a person too, since one candidate cannot be in two interviews at once. Times are handled in the viewer's own timezone throughout: formatting in UTC would put an 8pm IST interview on the wrong day for the recruiter who booked it. (2) **Interviewer availability and candidate self-booking** (Zoho F5), migration 027. A recruiter publishes a _run_ of times for a named candidate — publishing one at a time was the actual friction — and the candidate picks one in the portal they already have. Booking creates the interview and withdraws the other offers for that round, freeing the interviewer. The hard part is concurrency, not UI: booking is a **single conditional UPDATE** (`set status='Booked' where status='Open'`) and the caller checks the affected row count, so Postgres serialises two writers on the row lock and the loser is told the slot has gone. There is no read-then-write gap. A test asserts exactly one interview exists after two attempts on one slot. Every refusal — taken, not yours, does not exist, in the past — returns the _same_ message, so a candidate cannot probe for slots offered to other people, and the interviewer's name is withheld from the portal projection. 32 new tests (10 PGlite including the race, 12 domain, 10 user-flow); **518 tests total**. Still absent: email notification of an invitation, which needs a server.

- **Phase D shipped (28 Sep 2026):** assignment rules (Zoho I5), migration 028 — the last phase of the day-to-day plan. New candidates and demands arrived unowned, so nothing reached anyone's queue until a person noticed. Rules are **ordered** (first match wins, because without a defined order two overlapping rules make assignment depend on row order) and may only ever fill an **empty** owner — silently moving a colleague's candidate is worse than leaving one unassigned, and there is no audit story that makes it acceptable. Writing rules is **admin-only at the database level**: a recruiter who could write them could quietly route every incoming candidate to themselves, and a PGlite test proves the insert, update and delete are all refused. Every rule is dry-run before it is enabled, and a catch-up pass over existing records is previewed and broken down by assignee before it writes. Because ownership is free text, a rule assigning to a name no record uses is flagged rather than silently routing work nowhere. 15 new tests (4 PGlite, 11 domain, 8 user-flow); **541 tests total**. **Honest limit:** evaluation is client-side, like the existing workflow rules, so a record created through the API rather than the app is not assigned. A bug was fixed on the way: the candidate form defaulted `owner` to the literal string `'Recruiter'`, a placeholder that made "assigned to me" meaningless and stopped any assignment rule from ever firing — new candidates are now genuinely unowned until a person or a rule assigns them.

- **Remaining-features Phase 1 shipped (28 Sep 2026):** first-class placements and commercial outcomes, migration 029. A client account can record a candidate's planned, active, completed, terminated or cancelled deployment against the exact demand, with dates and delivery context. Bill rate, cost rate, billed amount and collected amount live in a separate administrator-only table; margin is derived. Candidate and client views use the real placement record instead of treating a pipeline label as the outcome. Composite foreign keys block cross-client/cross-workspace links, one live candidate-demand placement is permitted, both tables are audited and synced, and database tests prove recruiters cannot read commercials. **550 tests total.**

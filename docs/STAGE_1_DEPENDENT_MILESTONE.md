## Operator workflow and UI wiring

Administrators find the **Stage 1 dependent integrations** console after Settings → Integrations. Work hub provides a dependent-delivery section. Candidate Communication tabs in both the full repository and paged repository show the same console with the candidate UUID fixed. Demo mode and limited assessor/sales roles do not mount the console. Current internal viewers may read; recruiters may prepare/recover; only administrators configure connections, run diagnostics or change readiness. Server authorization remains authoritative after role changes. Privileged connection actions and diagnostic authorization enforce the existing workspace MFA policy.

1. Review Delivery sandbox readiness. Record a current administrator owner UUID, a connection label, purpose, cost/quota decision and acceptance evidence. References and evidence are plain metadata: do not paste passwords, API keys or sensitive candidate records here. Choose a fictional scenario and the optional secret reference. Save the configuration using its current conflict head.
2. Run the authenticated server sandbox diagnostic. It records the fictional capability and whether optional callback verification is configured. Review evidence and record a reason of 10–1,000 characters. Accept, then enable this generation. A diagnostic must match the generation and be no older than ten minutes; enablement requires its accepted state and acceptance within seven days. An enabled catalog entry means **fictional sandbox**, not a live sender.
3. In a candidate console, select an existing template version (latest 100 records listed; manual UUID supports others). Existing Communication tests provides template creation/versioning and contact/preference review. Supply demand/interview context if the template requires it. Preview the fictional exercise. Eligibility uses the real reviewed source, but the displayed/sink recipient is `fixture@example.invalid` and the subject/text are synthetic.
4. Optionally schedule in local browser time; the UI converts it to an ISO instant. Prepare the reviewed intent. The five-minute worker claims at most one intent per invocation. Refresh the bounded queue to inspect results. Provider accepted does not mean delivered. Duplicate/reordered scenarios generate fictional receipt events; success remains accepted until delivery evidence arrives.
5. Review an intent to see at most three attempts and 25 callback events per page. Queued/deferred/failed intents may be cancelled. Only eligible known failures below three attempts can be retried. Ambiguous/accepted intents offer reconciliation, never ordinary resend or cancellation. Record an explicit recovery reason. Unknown acceptance remains ambiguous when no authoritative fictional receipt exists; it awaits further reviewed evidence.

A lost mutation acknowledgement freezes the exact action, payload, reviewed head and operation UUID. Retry submits that same request. Discarding a retry requires reviewing server history before another write; it does not cancel a potentially committed operation. Candidate/source changes clear preview/history, scope/role changes remount the console, and late responses from the old scope are ignored. Refresh and page changes invalidate selected recovery evidence. Pages are live offset pages and may reorder; source heads protect writes rather than promising a stable queue snapshot.

## Contracts and bounds

The CLI-generated additive [migration](../supabase/migrations/20261008050701_dependent_stage1_delivery.sql) creates private `ecod_delivery_private.connections`, `intents`, `attempts`, `provider_receipts`, `events` and `receipts`, with candidate/due/history indexes, raw access revoked and RLS enabled. No browser role has raw table access. `api_delivery_sandbox` is an authenticated invoker wrapper around a guarded private definer. `worker_delivery_sandbox` and its private implementation are executable only by the server service role. The implementation uses an empty search path and explicitly qualified objects.

Browser actions: context, preview, history, diagnostic-token; administrator configure/accept/enable/pause/degrade/rotate/revoke; editor prepare/cancel/retry/request-reconcile. Mutation receipts are actor/workspace bound and exact request replays are checked before stale-source validation. New preparation binds candidate UUID, template/context, source head, actor, generation, schedule and expiry. Existing Anthro-ID identity remains untouched. Source checks prevent silent retargeting after merge; retained identity-family links remain readable for governance.

Limits: 25 queue/history rows plus a look-ahead record; offset 0–10,000; configuration/worker payload ≤16,000 bytes; callback body ≤8,192 bytes. Prepare at most 20 new intents per candidate identity family/24 hours and 500 pending intents per workspace. Schedule within 30 days ahead; tolerate at most five minutes past. Intents expire seven days after availability. There are at most three leases/attempts per intent and three distinct gated intents per candidate identity family/24 hours. Candidate locking at the final gate serializes that frequency decision; transient retries for the same intent do not count as new intent deliveries. UTC contact windows are inherited from existing preferences and checked at claim, final gate and sink. Deferred windows/frequency are revisited after an hour, definite transient failures after a minute.

Leases last 70 seconds. The Netlify runner has a 40-second application deadline, four-second RPC timeouts, one claim and at most three reconciliation records. Abandoned pre-gate leases may be reclaimed with a new lease/attempt; expired gated leases become ambiguous and are reconciled before further action. Completion requires the current unexpired lease; acceptance requires an existing provider receipt. The fictional sink is idempotent by intent ID. This is not a claim of exactly-once real network delivery. Final gate/sink rechecks narrow races; a future external request cannot be atomically cancelled by a database revocation after it starts.

Scenarios are success, transient, permanent, accepted-timeout, unknown, duplicate and reordered. Configuration updates, rotation and revocation increment generation; pending queued/deferred work is suppressed and stale leased work fails its final gate. Paused/degraded connections cannot dispatch. Revocation rejects old-generation callbacks. Historical receipts remain available for reviewed reconciliation; callback evidence cannot initiate a new send.

## Server configuration and verified callback intake

The three added functions are [delivery-sandbox-worker](../netlify/functions/delivery-sandbox-worker.js), [delivery-sandbox-diagnostic](../netlify/functions/delivery-sandbox-diagnostic.js) and [delivery-sandbox-callback](../netlify/functions/delivery-sandbox-callback.js). They reuse existing server Supabase configuration. Basic fictional dispatch needs **no new key, account or service**. The adapter's capability declaration explicitly reports fictional mode, idempotency, HMAC callback authentication, fictional receipt evidence and `live: false`.

Optional `DELIVERY_SANDBOX_CALLBACK_SECRET` is a Functions-only environment secret of at least 32 characters. The only accepted references are `none` and `env:DELIVERY_SANDBOX_CALLBACK_SECRET`; no secret value is returned to the UI or accepted as a connection property. This is a reference contract for the single sandbox verifier, not a production OAuth credential vault. Future adapters need their own scoped storage/rotation/permissions contract.

Callback endpoint: POST `/.netlify/functions/delivery-sandbox-callback`. Sign the exact raw UTF-8 body with HMAC-SHA256 over `timestamp + '.' + rawBody`; send lowercase 64-character hex in `x-delivery-signature`, and a ten-digit Unix-seconds value in `x-delivery-timestamp`. Timestamp tolerance is five minutes. The JSON object must contain exactly workspace UUID, intent UUID, positive generation, eventId (1–100 characters), messageId (`sandbox:<intent UUID>`), type (Provider accepted/Delivered/Bounced) and an ISO `at` instant. Events must reference an existing fictional provider receipt and current nonrevoked generation in the same workspace; event time is bounded to thirty days past/five minutes future. Base64 bodies, oversized bodies and unverified intake fail closed. Missing server secret returns 503; failed verification returns 401 before database access; rejected private intake returns a generic conflict response.

Event IDs deduplicate by workspace/generation. Exact duplicate bodies replay safely; the same ID with a different body conflicts. Reordering cannot downgrade delivery to acceptance; a later bounce may supersede delivery, while bounced is terminal. Durable intake precedes the response. Receipt reconciliation updates visible status in a bounded job. The diagnostic endpoint independently validates bearer/current workspace membership, administrator role and caller MFA policy before obtaining a current generation token; the service operation rechecks current administrator access. It returns redacted status rather than credentials.

## Privacy and recovery

Candidate-linked delivery intents, attempts, events, provider receipts and operation receipts join both inventories: **68 formal D7 categories / 65 operations source categories**. Recapture older captured scopes. Identity-family inventory includes historic aliases/merged records. Actor-only integration metadata is not a per-candidate record. Existing D6 notices explicitly exclude the new internal delivery journals; regenerate reviewed access packages after the scope notice changes. These decisions do not add an erasure executor or silently disclose integration journals.

Full recovery must include this private schema, operation/provider receipts, lease/reconciliation state, connection generations and secret references, all earlier private/public schemas, Auth identities and private object versions. Store callback secret material separately under existing server key custody; database exports contain references only. Restores must pause outbound policies/connections until receipt and generation state is reconciled. Stage 2 will implement operational backup/restore acceptance; app JSON exports are not a full backup.

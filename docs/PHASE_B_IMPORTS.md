# Phase B1 — Saved spreadsheet reviews and atomic background imports

Implemented locally on 6 October 2026. This is the first Phase B slice, not completion of Phase B. [Durable CV staging/extraction](PHASE_B_CV_STAGING.md) and [paged startup/browsing](PHASE_B_PAGED_REPOSITORY.md) are now opt-in local slices; legacy workflows and hosted acceptance remain pending.

## Recruiter workflow

In cloud mode, **People → Import → spreadsheet mapping → review** now saves a durable review instead of directly writing all candidates. CSV and XLSX use the same path. Parsed rows and mapping are persisted in the database in pages of 50, with a SHA-256 fingerprint of the parsed source. Saving does not authorize import.

Open **Saved spreadsheet imports** in the importer or workspace settings, inspect/correct the saved rows and click **Approve background import**. The scheduled worker processes at most 20 rows per invocation, even when the browser is closed. Refresh the saved-import panel for progress, then refresh the repository to load completed profiles. The app does not yet push job updates into the open candidate table automatically.

Contact and other imported fields can be corrected. Unsaved edits block approval and page changes. Skipped/excluded rows require explicit correction and save before being reconsidered. Nothing is auto-merged. Duplicate email/phone/LinkedIn records are skipped and reported. Duplicate LinkedIn identity checks now serialize through a database trigger for future writes, including UI/API writes; pre-existing duplicates are left for reviewed merging.

If staging was interrupted, reopen the partial batch through the importer, choose **Resume staging this spreadsheet** and reselect the original file. Its parsed-content fingerprint must match. Existing row IDs are reused, and an incomplete batch cannot be approved. The original spreadsheet file itself is not uploaded; the parsed review is persisted. If the source is unavailable, cancel that incomplete batch and create a new import from available data.

Failed rows can be reopened, corrected and explicitly reapproved. Successful rows remain read-only and are never replayed. Cancellation stops remaining work and keeps completed candidates. Approval becomes paused if the approving user loses editor access; another editor must reopen/review/approve it.

## Atomicity and authorization

- Database rows and manifests are accessible only to editors in their active workspace. Viewers and anonymous users cannot read drafts or invoke import mutations.
- Client-supplied UUIDs, Anthro-ID allocations, workspace IDs and unrelated fields are removed from staged payloads. Candidate UUIDs are generated by the server and Anthro-ID is allocated by the existing candidate trigger.
- Manifest reuse, row upserts and optimistic versions protect retries and concurrent reviews. Approval requires every expected row to have been staged.
- The worker locks a batch with `FOR UPDATE SKIP LOCKED`; candidate insertion and row completion occur in the same transaction. Worker failure/rollback cannot leave a successful candidate without its receipt. Retrying after a crash repeats only uncommitted work. Each row uses a subtransaction so a rejected row does not stop valid rows.
- This database-only commit step needs no external-effect lease: locks and transaction rollback own recovery. CV parsing, scanning and email still require their separate leased workers.
- Sequence values consumed by failed/rolled-back inserts are not reused. Gaps in Anthro-ID numbers are expected.
- Approval/cancellation/reopening are audited without copying raw draft payloads into logs. Candidate creation still emits normal history, lifecycle and integration events. Draft data is PII and needs the later retention workflow; no automatic draft erasure is delivered here.

Local PGlite verifies 200 synthetic spreadsheet rows, not the blueprint's 200-real-CV acceptance scenario.

The default CV importer remains browser-based without quarantine. The new [durable CV staging preview](PHASE_B_CV_STAGING.md) has isolated extraction and requires a workspace flag. Integrate Phase C's private scan gate before production activation; neither slice is finished antivirus scanning.

## SHA-256 compatibility fix

The existing file helper truncated SHA-256 to 32 hexadecimal characters. New uploads now retain all 64 characters, enabling VirusTotal hash lookup and source-fingerprint checks. Old truncated fingerprints cannot be expanded mathematically; their original files must be read and rehashed before VirusTotal can use them. This migration does not backfill those files or transmit CVs to VirusTotal.

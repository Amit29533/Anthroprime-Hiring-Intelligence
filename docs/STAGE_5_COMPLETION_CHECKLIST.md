# Stage 5: operations and governance

Implements continuation milestone 5 in the [five-phase audit](FIVE_PHASE_IMPLEMENTATION_AUDIT_2026_10_07.md#next-build-order), on the existing Netlify/Supabase stack. This is the local implementation and acceptance tooling for that milestone. Hosted acceptance and approved recovery/retention execution are separate gates; this document does not certify all original DOCX requirements.

## Workflows

| Feature | Behavior |
| --- | --- |
| Operations console | Settings → Operations and governance. Current administrator membership and optional privileged MFA are required on every RPC, including receipt replay. |
| SLA policy | Versioned subject-review days, proposal/response review hours and task grace hours. UTC elapsed time; explicit subject-case due dates take precedence and expire at the end of that UTC day. Task grace starts after the end of its due day. Targets do not rewrite existing deadlines or represent legal deadlines. |
| Internal notice preferences | Repository overview → Internal SLA review. Per-account, per-workspace opt-in and UTC quiet start/end. Equal hours mean no quiet window; windows can cross midnight. Quiet/paused notices leave the current review queue available. Viewers can save their display preferences; limited external/sales/assessor accounts cannot use the internal RPC. Administrators must satisfy the existing MFA gate before seeing subject-case metadata. |
| Retention policy | Versioned month window and explicit 10–500 character policy reference. Selects profiles with missing or old verification dates for review. Future dates are flagged in job evidence. The legacy cloud retention form is replaced by this control; demo retention remains separate. No policy approval or erasure is inferred from saving a reference. |
| Candidate selection | Bounded name/Anthro-ID search with current-identity, retention-due or hold filters, 25-row pages. Add individual rows or enter 1–250 unique compact Anthro-IDs. Cross-workspace, unknown, retired, duplicate or over-limit selections fail atomically. The selection is frozen, not silently replaced with the browser's current page. |
| Selected profile reports | Curated Anthro-ID, verification/status/hold, owner/action, retention/future-date flags and current identity-family subject-case count. No name/contact, compensation, documents, arbitrary JSON or internal source hash in exports. Represents the explicit selection, not whole-repository completeness or readiness certification. |
| Retention/subject coverage jobs | The same curated review facts with a frozen policy window/reference. Each result opens the existing scoped subject-request workflow, where the administrator can create, verify, assign, plan and review a case and its access/erasure coverage. Jobs do not open cases automatically or infer verified identity. |
| Erasure dry runs | One identity family per batch, counts for the 57 pre-operations source categories, source-change detection and explicit manual exclusions. Records only a preview. The full reviewed D7 inventory separately covers 60 categories including operations jobs/items/receipts. Dry-run source comparison intentionally excludes its own changing operations metadata so recording results does not invalidate itself. Those metadata remain covered in the formal D7 scope and require review. |
| Bulk owner/action jobs | Frozen before/after previews; all items must be Prepared before explicit confirmation. Confirmation rechecks every source/hold, the policy version and a 24-hour preview lifetime. Application rechecks each item and uses the existing permission/audit-aware quick-edit API. It changes only owner/next action, preserves verified facts, and rejects held or retired identities. Blank proposed values explicitly clear fields. |
| Resume and recovery | An operator processes at most 10 report/retention/bulk items, or one erasure scope, per call. Closing the browser leaves durable work in the database; reopen history to continue. No additional scheduled worker or service is needed. Successful batches remain committed; cancellation stops remaining work and does not undo applied changes. |
| Failure recovery | Per-item transactions isolate failure. SOURCE_CHANGED or a generic SQLSTATE code appears without source/error text. Re-prepare failed/stale items explicitly, up to five attempts. Bulk jobs with any applied item require a new selection rather than re-preparing already committed work. A job marked Completed has finished processing; only an entirely successful job can export. Review counts distinguish failures. |
| Queue health | Current workspace counts for workflow, index, interview/freshness reminder, communication-test and operations queues; oldest workflow/index timestamps and global worker heartbeats. Use the existing queue-specific panels for their guarded retries. A heartbeat is not delivery, workspace coverage, scheduler reliability or hosted recovery proof. |
| Redacted evidence | Administrator-authorized JSON health and selected-job exports with actor-bound receipts and server audit events. Health includes counts/timestamps/queue names only. Job exports are limited to 250 items and 2 MiB. Each export family is limited to six new exports per actor/workspace/minute; exact receipt retries do not consume another export slot. |
| Backup honesty and restore tests | App JSON downloads disclose loaded/possibly partial application rows and exclude private schemas, Auth, original bytes, protected/unloaded data and database configuration. They are portability artifacts, not full disaster-recovery backups. Embedded database snapshot tests exercise private-job/receipt/grant restoration and non-recycled Anthro-ID allocation. |

## Security and consistency

`ecod_ops_private` contains policy, preferences, jobs, items and receipts. Every table has RLS enabled and raw application privileges revoked. Only guarded private entrypoints and public invoker wrappers are granted to authenticated users. Helpers, source inventories and private hashes remain ungranted. Public APIs are `api_operations` and `api_sla_worklist`; no destructive executor or live transport API is introduced.

Operator mutations serialize within the workspace, then lock candidate rows in UUID order before the job journal. Preparation/application locks only the next bounded batch; confirmation/export can lock the explicit selection, capped at 250. Membership share locks prevent role removal from racing an in-flight authorization check. True independent-session behavior still requires hosted verification.

Receipts bind operation UUID, current workspace, actor, action, job, version and exact JSON payload. A changed request conflicts; unchanged retries return the original result after current access/MFA checks. The console freezes pending requests after a lost acknowledgement, disables dependent controls and offers exact retry or explicit local discard with a server-history warning. Scope changes/unmounts suppress late responses. Policy/job version conflicts require refresh.

Jobs are capped at ten active jobs/workspace and 50 creations/day/workspace. Work must start/resume within seven days; stale report/dry-run exports fail and require a fresh job. Bulk applied exports describe the historic preview and per-item application timestamp, not a current-profile report. Candidate updates, merges and holds are checked at their relevant boundaries. New report/retention exports also compare identity-family subject-case versions and the UTC date, so case changes or date rollover require fresh evidence. Exact existing export receipts replay the original reviewed snapshot after current access/MFA checks; they do not relabel it as current. Selected reports include held identities for governance review; bulk processing does not.

Original D7 identity/record limits remain 100 related identities, 2,000 rows/category and 10,000 total. An excessive scope fails that item; it is never presented as a complete partial inventory. Dry-run counts cannot establish object existence, external copies, operator downloads, arbitrary text references, unlinked private receipts or backup erasure. Use the formal subject-request checklist and approved manual evidence for those areas. D6 access-package exclusions now name operations metadata/results/receipts; they are not silently included in candidate disclosure packages.

## Local verification

See `tests/migration-stage5-operations.test.js`, `tests/ui-stage5-operations.test.js`, the existing privileged-MFA suite and backup-integrity suite. Coverage includes migration replay, raw/helper denial, roles/tenants, current access on retries, exact receipts, policy/job conflicts, old/held sources, independent bulk preview/application, partial cancellation, failure isolation/recovery, export redaction/quotas, retention selection, UTC notices and backup scope.

The synthetic workload creates 250 fictional profiles with 1,000-character next actions, runs 25 ten-item batches, checks exact replay and one attempt per item, then pages ten 25-row results and exports the selection. Response budgets are checked below 50,000 bytes/page and 400,000 bytes/export for this fixture. This is local correctness/volume evidence, not a production latency or capacity guarantee. The embedded snapshot restores PostgreSQL application roles/functions/private records and checks a durable operation replay and forward-only compact-ID allocation; cached sequence values may be burned during recovery and must never be recycled.

Final verification: **888 Node regression tests passed**, with zero failures, cancellations or skips (437.7 seconds), plus four Python OCR tests. The last focused run passed all 11 Stage 5 database scenarios after the final source/version/selection guards. Six dedicated React DOM workflow tests and the existing MFA/cloud-startup suites passed. ESLint finished without warnings, changed-file Prettier, documentation local links, script syntax and Git whitespace checks passed. Netlify offline production packaging completed with all 18 functions and a 67.7 KiB main entry against its 100 KiB budget. The first complete run had five older-fixture failures: three local-date/UTC assumptions, a fixture deliberately deferring migration 039, and an assertion for the superseded cloud retention control. UTC fixture dates, correct dependency ordering and current UI assertions were corrected; the final full suite passed.

Local Supabase advisors could not connect to `127.0.0.1:54322` because the local server is not running. No hosted Auth/PostgREST, independent-session concurrency, provider scheduler, hosted workload/restore or accessibility acceptance is claimed. No GitHub push, hosted migration, deployment, external send or erasure was performed.

## Activation and hosted acceptance

1. Preserve a recoverable database backup **including every private schema, Auth, functions/policies/grants, sequence state and application data** and separate original-object backups. Record recovery ownership, retention approval, RPO/RTO and storage/provider-copy coverage. Test in a disposable restored environment, never by overwriting production.
2. Apply the full sorted migration chain through `20261007190524_stage5_operations_governance.sql`. This migration is CLI-generated, replay safe and does not enable notices or destructive processing. No package, function, environment variable or provider is added to the app.
3. Deploy frontend and existing 18 Netlify functions together after acceptance. Recapture D7 scopes and regenerate reviewed D6 packages after the new inventory/exclusion changes. Existing dry-run source snapshots describe the pre-operations registry; future migrations adding candidate-linked data must update the source inventory as well as D7 and invalidate/recapture old jobs as needed.
4. Exercise both workspaces and every role through real Auth/PostgREST, including AAL1/AAL2, revoked membership, client-only accounts, exact retries and private schema denial. Test current holds/merges between preview, confirmation, batches and export.
5. Run `node scripts/stage5-hosted-acceptance.mjs` in a disposable staging workspace with two independently signed-in administrator sessions. Configure `ANTHRO_ACCEPTANCE_DISPOSABLE=true`, `ANTHRO_ACCEPTANCE_URL`, `ANTHRO_ACCEPTANCE_ANON_KEY`, `ANTHRO_ACCEPTANCE_JWT_A`, `ANTHRO_ACCEPTANCE_JWT_B`, `ANTHRO_ACCEPTANCE_WORKSPACE` and `ANTHRO_ACCEPTANCE_IDS` (1–10 fictional compact IDs). Store values securely; do not paste tokens into logs. The script verifies both workspace IDs **before creating work**, then exercises real simultaneous versioned mutations, replay and redacted export. It creates retained report jobs/audits; it sends nothing externally and changes no candidate profile. It is intentionally excluded from build/test automation and has not been run against a hosted project.
6. Repeat representative workload acceptance at realistic identity-family/category volumes. Measure RPC latency, locks, contention, Netlify worker backlog, quiet-window boundaries, retries, storage growth, stale source rates and usage limits. Record workload and environment alongside results; do not extrapolate the synthetic local timings into a hosted SLA.
7. Run security/performance advisors and independently review private schema privileges/index plans. Restore a complete staging backup, reconcile object availability and identity sequence high-water values, verify grants/receipts/holds/worker policies, and keep outbound/test policies paused during restore until reviewed. A recovery artifact does not prove external-copy erasure or live-provider delivery.
8. Check keyboard navigation, labels, error/retry focus, mobile overflow and actual browser downloads against the deployed UI. Local React DOM tests are behavior evidence, not an accessibility certification.

Rollback: stop operator batches, pause notice and existing worker policies, and retain job/receipt/history evidence. Reverting the UI does not remove server checks. Do not delete receipts or reset compact-ID sequences to force a retry. Real erasure, external sends, hosted migrations and deployment remain outside this local implementation.

Implementation follows the official [Supabase database-function security guidance](https://supabase.com/docs/guides/database/functions) and [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security). The [September 2026 PostgreSQL breaking-change notice](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes) was reviewed; this stage introduces no ltree/btree_gist indexes, legacy-cipher pgcrypto calls or custom operators.
